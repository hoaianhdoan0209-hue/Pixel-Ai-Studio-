# VI. GITHUB INTEGRATION — KẾT NỐI MÃ NGUỒN THẬT

Đây là một phân hệ tích hợp trực tiếp với Studio và Projects.

## 1. Kết nối GitHub

Cho phép tài khoản có quyền:

## 2. Quản lý repository

Trong trang Project, tạo tab **Source Code**.

Hiển thị:

- Repository.
- Branch.
- Commit.
- Người commit.
- Thời điểm.
- Tệp thay đổi.
- Lịch sử thay đổi.
- Pull Request.
- CI status nếu có.

Các chức năng phù hợp:

- Xem cây thư mục.
- Xem mã nguồn.
- Xem diff.
- So sánh commit.
- Liên kết commit với nhiệm vụ.
- Xem trạng thái kiểm thử.

## 3. AI làm việc với GitHub

Quy trình ưu tiên:

1. Chủ dự án cấp quyền repository.
2. AI đọc yêu cầu.
3. AI lấy mã nguồn vào workspace an toàn.
4. AI tạo nhánh riêng.
5. AI thực hiện chỉnh sửa.
6. AI chạy kiểm thử.
7. AI tạo diff.
8. Người có quyền kiểm tra.
9. Khi được phê duyệt, AI tạo Pull Request.
10. Người có quyền quyết định merge.

Không cho phép AI mặc định ghi trực tiếp vào main branch.

Không tự ý force push, xóa repository hoặc thay đổi cài đặt bảo mật.

## 4. Đồng bộ

Hỗ trợ GitHub webhook có xác minh chữ ký.

Khi có commit hoặc Pull Request mới, cập nhật thông tin liên quan trong Project.

Phải xử lý idempotency để sự kiện gửi lại không gây tạo dữ liệu trùng.

## 5. Điều kiện hoạt động

Nếu chưa kết nối GitHub, chức năng hiển thị trạng thái chưa kết nối và hướng dẫn cấu hình.

Không được tạo commit, PR hoặc lịch sử GitHub giả.

## 2. Các nền tảng

Kiến trúc có khả năng hỗ trợ:

- HTML5/Web.
- Android APK.
- Windows.
- Linux.
- Các định dạng tương thích khác.

Không được giả định tất cả nền tảng đều có thể build trên cùng một máy chủ.

Chỉ kích hoạt pipeline khi đã cấu hình SDK, công cụ build và runner phù hợp.

## 3. Build pipeline

Các bước:

1. Nhận mã nguồn hoặc commit.
2. Chọn cấu hình build.
3. Xác thực quyền.
4. Tạo build job.
5. Đưa vào hàng đợi.
6. Chạy trong runner cô lập.
7. Thu thập stdout, stderr và exit code.
8. Kiểm tra kết quả.
9. Lưu artifact.
10. Liên kết artifact với dự án và phiên bản.
11. Gửi thông báo.

Phải ghi nhận trạng thái:

- Queued
- Preparing
- Building
- Testing
- Succeeded
- Failed
- Cancelled

## 4. Preview

Game web được chạy trong môi trường sandbox và domain cô lập nếu cần.

Không cho mã nguồn tùy ý truy cập cookie, token hoặc tài nguyên của website quản trị.

Các bản build tải lên không được tự động chạy trên máy chủ chính.

## 5. Quản lý bản phát hành

Cho phép:

- Đặt version.
- Ghi chú cập nhật.
- Gắn artifact.
- Đánh dấu bản thử nghiệm.
- Đánh dấu bản ổn định.
- Quản lý quyền tải.
- Công khai bản phát hành.
- Liên kết sang diễn đàn.

Mỗi artifact cần có metadata, kích thước, hash và thông tin build.

# XVIII. KIỂM THỬ TÍCH HỢP BẮT BUỘC

Kiểm thử các quy trình sau:

**Scenario A: Community**

Đăng nhập → Đăng game → Người khác xem → Bình luận → Nhận thông báo.

**Scenario B: Customer Request**

Khách hàng tạo yêu cầu → AI Planner phân tích → Tạo Project → Tạo Tasks → Khách hàng xem tiến độ.

**Scenario C: Collaboration**

Owner mời Developer → Developer chấp nhận → Nhận nhiệm vụ → Hoàn thành → Owner duyệt.

**Scenario D: GitHub**

Owner liên kết repository → AI tạo nhánh được ủy quyền → Chỉnh sửa code → Tạo diff → Chạy test → Tạo Pull Request sau phê duyệt.

**Scenario E: Build**

Chọn commit → Tạo build job → Runner xử lý → Lưu log → Lưu artifact → Người dùng tải bản build.

**Scenario F: Customer Revision**

Khách hàng báo lỗi → Tạo Customer Request → Chuyển thành Task → Agent xử lý → Kiểm thử → Khách hàng nghiệm thu.

**Scenario G: Security**

Người không có quyền cố gắng xem repository hoặc dự án riêng tư → Backend từ chối.

**Scenario H: Project Lock**

Owner khóa dự án → Thành viên không có quyền không thể sửa → Owner mở khóa → Quyền chỉnh sửa được khôi phục.

**Scenario I: AI Budget**

Đặt ngân sách → Chạy tác vụ → Ghi token và chi phí → Chạm ngưỡng → Gửi cảnh báo → Áp dụng quy tắc giới hạn.

**Scenario J: Persistence**

Đăng tải dữ liệu → Refresh → Đăng xuất → Đăng nhập lại → Dữ liệu vẫn còn đầy đủ.

**Scenario K: Concurrent Updates**

Hai thành viên sửa cùng đối tượng → Hệ thống phát hiện xung đột hoặc xử lý cập nhật an toàn → Không ghi đè âm thầm.

**Scenario L: Integration Failure**

Ngắt kết nối AI/GitHub/runner → Hệ thống báo lỗi đúng → Không ghi nhận tác vụ giả → Có thể khôi phục khi kết nối trở lại.

# XIX. QUY TẮC LÀM VIỆC DÀNH CHO CODEX

1. Trước khi code, kiểm tra repository, cấu trúc thư mục, dependency và các chức năng đang tồn tại.

2. Nếu đã có dự án, kế thừa và cải tiến; không phá hủy dữ liệu hoặc tính năng hoạt động.

3. Lập kế hoạch ngắn gọn theo từng phase, nhưng không dừng ở lập kế hoạch.

4. Triển khai mã nguồn thực tế.

5. Tạo migration khi thay đổi database.

6. Viết test cho các chức năng quan trọng.

7. Chạy lệnh kiểm thử có thể thực hiện trong môi trường.

8. Sau mỗi phase, báo cáo những gì đã hoàn thành và lỗi còn tồn tại.

9. Không tuyên bố đã kiểm thử khi chưa thực sự chạy test.

10. Không tuyên bố đã build APK hoặc tạo artifact nếu tệp đầu ra không tồn tại.

11. Không dùng mock data thay thế dữ liệu thật trong production.

12. Nếu một tích hợp cần khóa API hoặc quyền bên ngoài, triển khai cấu trúc cần thiết và hướng dẫn cấu hình; không tự tạo thông tin kết nối giả.

13. Không tự ý push, merge, deploy production hoặc thực hiện thao tác phá hủy nếu chưa được cấp quyền.

14. Ưu tiên code rõ ràng, module hóa, có thể bảo trì.

15. Đảm bảo sự phụ thuộc giữa các phân hệ được xử lý đúng.
